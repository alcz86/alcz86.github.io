Fleet Observability: Four Ways an Agent Lies About Being Alive

Once you run a fleet of scheduled agents rather than one, the hard question stops being "does it work" and becomes "would I know if it stopped". I built the answer: a heartbeat spine, a daily classifier, and side-effect probes for the agents that can't report on themselves — after four separate incidents where every health signal was green and the work had quietly stopped.

01The problem: liveness is not one signal

Every scheduled agent I ran had a health check. All of them passed. And four times, in four different ways, the work had stopped anyway.

The pattern behind all four is the same: the thing being measured was a proxy for the thing that mattered. A process exists. A file was written. A CI badge is green. None of those are "the agent accomplished its job." Once that gap opens, a monitor doesn't just fail to help — it actively manufactures confidence.

The design principle Measure liveness by work output — not by process existence, and not by heartbeat freshness alone. A heartbeat proves that code ran. It does not prove that anything was accomplished. Those must be two separate signals, or a failing agent will write a perfectly fresh heartbeat about its own failure forever.

02The four lies

Each detector in the system exists because one of these happened in production.

Lie 1 · Process

"The session is up" — for 22 hours of nothing

An always-on agent sat at an idle prompt for 22 hours. The multiplexer session existed, the PID existed, the scheduler reported loaded. Every process-existence check said healthy.

Fix: liveness = a heartbeat written by the work itself, never by the launcher or the monitor — plus a grace window for young sessions, so "hasn't run yet" isn't mistaken for "dead" and double-armed.

Lie 2 · Blindness

"Scanning on schedule" — and seeing nothing, for 17 hours

Two individually correct decisions cancelled each other. The agent wrote a heartbeat on the failure path (so failures wouldn't be silent — good), and liveness keyed on heartbeat freshness (reasonable). Together: a blind agent wrote a fresh failure-heartbeat every 10 minutes and every check reported healthy. "Did work" and "saw anything" had collapsed into one signal.

Fix: a distinct blind classification — the last k runs all errored and all saw zero items. Requiring all k means a flaky call or a single upstream 5xx stays errors and never triggers a restart.

Lie 3 · Threshold

A staleness window wider than the cadence

Weekly agents were allowed 200 hours of silence. An agent that skips its one weekly slot sits at ~168h — comfortably under the limit. Three agents were dead for roughly six weeks behind a green OK — ran 168h ago.

Fix: allowed_age = cadence + small slack, never cadence × 1.2. A healthy agent has just run when the digest checks it. If the threshold tolerates a whole skipped cycle, healthy and dead are indistinguishable by construction.

Lie 4 · Green CI

A passing run that did nothing

A shell wrapper ran five scripts, captured each exit code into a log line, and never acted on it — so the job's exit status was that of the final echo. Three of five steps died and CI went green. Separately, a notifier designed to be non-fatal returned False on a runner where its local CLI didn't exist: green run, nothing posted, nobody told.

Fix: a pass is only meaningful if a failure could have made it fail. Tally failures and exit non-zero; callers must check non-fatal return values and raise. Verify migrations by reading per-step conclusions, never the run badge.

03Architecture

Three small stdlib-only Python modules and one scheduler entry. No service, no database, no dependency the agents don't already have.

agent_heartbeat.py     shared helper — the write side
  record(agent, status, **fields)  → artifacts/agent_heartbeat/<agent>.json
  freshness_lag_days()             → is the INPUT data current?
  content_health()                 → did the run actually see anything?
  CLI: agent_heartbeat.py record <agent> <status> [k=v ...]
       ← any script, any language, any repo, one line

fleet_remote_checks.py  side-effect probes — for agents that can't write here
  cloud CI agents are checked by querying a SPECIFIC workflow's last run,
  then a heartbeat is written ON THEIR BEHALF → the digest reads one format

fleet_health_digest.py  the read side — classify + notify
  for each agent in INVENTORY:
      OK | SILENT (didn't run) | UNHEALTHY (status != ok) | MISSING
  cadence-aware windows: weekday_only (30h, 78h over a weekend) | weekly (174h)
  posts ONE chat message if anything is wrong — SILENT ON GREEN
  --daily forces a post · --dry-run suppresses it

launchd  →  weekday mornings, one run, one message

The important structural choice is the uniform read path. Agents running on a laptop write their own heartbeat file; agents running in cloud CI can't, so a probe checks their side effects and writes the heartbeat for them. The classifier never learns the difference — which means adding an agent is one inventory entry, not a new monitor.

04The rules that make it not lie

RuleWhy — the failure it prevents
Heartbeat on success and on crash — wrap the entry point in try/exceptA crash before the success-path write leaves no file at all. The agent looks quiet, not broken, until the staleness window trips hours later.

Diagnostic tells that a monitor is lying to you

Worth internalising, because they generalise well beyond agents:

  • A verdict quoting a suspiciously round multiple of the cadence (168h = exactly 7 days) yet reading OK.
  • Byte-identical timestamps across independent agents — jobs on different schedules cannot finish in the same second. That's a backfill writing fabricated heartbeats.
  • Zero-byte stdout and stderr on a job that "ran" — the failure precedes any program output, so it's in the wrapper, not the program.
  • Before calling a monitor's output stale, check the monitor's own schedule — a weekend gap in a weekday-only digest looks exactly like a dead publisher.

05Detection without authority is not recovery

The most expensive lesson in the project, and the one I'd keep if I could keep only one.

During the 22-hour outage the watchdog diagnosed the problem perfectly. It went stale, alerted once, then logged status=stale (prev=stale) more than eighty times while nothing on the machine was willing to restart anything. Alert-only is a half-loop.

The root cause was a good principle leaking out of its lane. "Propose, never auto-apply" is exactly right for permission and allowlist changes — widening what an agent may do unattended is a security decision that belongs to a human. But that posture had spread into the liveness path, where restarting a dead loop is not a security decision at all. So I split them explicitly:

ConditionAuthorityTrigger style
stale / down — the loop isn't runningAuto-recover: restartEvery tick while unhealthy
blind — running, producing nothingAuto-recover: kill first, then relaunchEvery tick while unhealthy
stuck — waiting on a permission promptHuman-gatedEdge-triggered alert

Two details that look like pedantry and aren't. Kill before relaunch for blindness: the launcher's own liveness test is heartbeat freshness, which a blind agent passes, so a plain "start if not running" is a no-op. And not edge-triggered for the auto-recover states: a blind or dead agent does zero work, so there is no new edge to fire on — one failed recovery attempt would otherwise leave it dead forever.

The question I now ask of every monitor I add: if this fires, what is allowed to act on it? If the answer is "nothing", I've built a notification, not a control loop.

06What it caught

  • A published dashboard serving 16-day-stale data — the pipeline was frozen upstream, the publisher ran happily every morning, and every check was green. The freshness signal is what surfaced it.
  • The crash blind-spot: agents that died before writing a success heartbeat and therefore looked merely quiet.
  • Three weekly agents dead for ~6 weeks behind a threshold wider than their own cadence.
  • A retired job still in the inventory — the digest is also a census, so decommissioned work stops being ambiguous.
  • A backup job wedged for two days at exit code 0: a shell conditional caught the push rejection and logged it instead of raising. It had alerted, into a channel nobody watched — an alert nothing watches is not a signal.

Generalisation Laptop-only assumptions fail silently in the cloud. Every migration failure I hit had the same shape — a hardcoded home-directory path, a CLI that only exists on the workstation, user-scoped OAuth credentials. On a shared runner these raise at import or return falsy, and any non-strict wrapper converts that into a green tick. Grepping for those three shapes before moving a job to CI is now a standing step.
